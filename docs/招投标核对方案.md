# 招投标核对 · 方案与升级

结论先行：**不开新项目，把这一条链路做透。** 现有实现约七成，缺的不是方向，是**一组能贴进简历的数字**。

个人项目。数据用政府采购网公开的招标文件，公司情况自己写一份 `company.yaml`。不生成整本标书，不判断能不能中标。

---

## 一、它解决什么问题

一份政府采购招标文件通常一百到两百页，废标条件、资格要求、评分表、材料清单分散在不同章节，而且用词极像。「保证金」「资格」「业绩」在投标人须知、评分办法、采购需求、合同里都会出现。

普通 RAG 整份一起搜，经常把评分办法里的「业绩加分」当成资格门槛，或者把合同里的履约保证金当成投标保证金。本项目先判断问题该去哪一章，再只在那一章里检索。

## 二、为什么是它（而不是讨论过的那六个方向）

判断一个项目该不该用 AI，只有一条尺子：

> **规则写得出来，就写代码；规则写不出来的地方，AI 才真在干活。**

| 方向 | 规则写不出来的地方 | 裁定 |
|---|---|---|
| 投递管理 / 求职助手 | 基本没有（几十条数据、七个字段） | AI 是装饰 |
| 故障诊断 Agent | 有，但拿不到真实运维数据 | 做不了 |
| 代码库记忆 | 有，但通用 Agent + `git log` 就能替 | 过度设计 |
| 制度换版 | 制度几年才改一次，冲突场景触发不了 | 硬凹 |
| 教学 Agent | 大模型自带教学能力 | 多余 |
| 中文文档解析评测基准 | 字节 CC-OCR V2、PureDocBench 已占位 | 做不过 |
| **招投标核对** | **版式千变万化、跨页表格、页码坐标——正则写不出来** | **成立** |

所以它不是备选，是唯一。

## 三、真实数据长什么样

找到的公开招标文件都是一个 PDF 按章节排，不是一包十几个文件。常见章节：

| 章节 | 里面有什么 |
|---|---|
| 招标公告 / 投标邀请 | 预算、最高限价、资格要求、截止和开标时间 |
| 投标人须知 | 保证金、投标有效期、密封签章、无效投标情形 |
| 资格审查 | 资格证明材料清单 |
| 评标办法 | 评分项、分值、实质性条款（常用 ★ 标出） |
| 采购需求 | 技术规格、服务要求、数量 |
| 合同文本 | 付款、履约保证金、违约责任 |
| 投标文件格式 | 投标函、开标一览表、声明函等空表 |

所以路由的单位是「章节」，不是「文件」。章节靠目录和标题切出来，切不准的用模型看标题和前几行判一次。

## 四、输入输出（已实现）

输入：一份招标文件 PDF + `company.yaml`（成立年限、资质证书、人员证书、近三年业绩、是否中小企业、能否交保证金）。

输出四张主表、两张辅助表，加一个提问框：

| 表 | 每行内容 |
|---|---|
| 废标对照 | 条件原文、出自哪章哪页、对照 `company.yaml` 的结论（满足 / 不满足 / 人工看） |
| 评分对照 | 评分项、分值、评分标准原文、页码、公司已有的对应材料 |
| 材料对照 | 必须提交的证明材料、页码、YAML 里有没有 |
| 空位对照 | 投标文件格式里要填的表和字段，只列出来，不代填 |
| 时间节点 | 获取文件截止、投标截止、开标、质疑期限，各带页码 |
| 合同要点 | 付款方式、履约保证金、违约责任、验收，各带页码。只是中标后的约束，和废标表分开 |

规则三条，不能破：

- 每一行都必须有页码。没有页码或模型没把握的，统一标「人工看」，不猜。
- 废标表最前面单列带 ★（或 ▲）的实质性条款：先正则抓标记，再由模型确认是不是「不满足即无效」。
- 提问框只回答这份文件里的事（如「联合体能不能投」「开标在哪」），带页码；找不到就说「文件中未找到」。

界面（Streamlit，`app.py`）：点任意一行，右侧用原件页图翻到对应页，按块坐标画高亮框；没有页码或坐标的不画框。可切到解析文本视图核对章节切分。所有表导出 Excel。演示页见 `static/index.html`。

## 五、现状（代码是唯一事实）

**已跑通**

- 版式解析：PyMuPDF 按页抽文本并保留块坐标 `bbox`，按目录切章、用别名标类型，章内切块（带章节、页码、bbox）
- 检索：按章节类型分库的 BM25 + FAISS
- 核对主流程：LangGraph 固定四步，`data/step_output/` 分步落盘，页面显示后台进度
- 提问框：最多 5 步工具循环
- 回归集：`eval/questions.json` 8 条人工对着 PDF 原文核过页码的题，`eval/compare.py` 直接给 check 输出打三档分（absent / miss / hit）
- 离线单测 15 例：章类型归并、切章、无页码降级、`company.yaml`

**规模**：`tender/` 约 1520 行，加 `main.py` / `app.py` / `tests` / `eval` 约 2070 行。样本 3 份公开招标 PDF 已在 `sample/`。

**缺的四件**

1. 多 Agent 分工（现在是单链路，出错无法定位到环节）
2. 独立校验层（防幻觉）
3. 自进化回路（归因 → 规则 → 回归）
4. 可观测（哪一层错了能定位）

## 六、当前链路：固定工作流 + 两处 Agent

```text
PDF -> 按页抽文本并记 bbox -> 按目录切章节并标类型 -> 章节内切块（章节、页码、bbox）
                                         |
                      BM25 + 向量索引（按章节类型分开）
                                         |
LangGraph 固定四步：
  1 废标：只搜 招标公告 + 投标人须知 + 资格审查
  2 评分：只搜 评标办法
  3 材料：只搜 投标人须知 + 资格审查 + 投标文件格式，再对 company.yaml
  4 空位：只搜 投标文件格式
                                         |
            每条检查有没有页码 -> 有：进表；没有：人工看
                                         |
                    四张表 + 提问框（先判章节再检索）
```

四步是每次都跑的固定任务，不是等用户提问，所以这部分是工作流，不叫 Agent。模型只做三件事：给切不准的章节分类、从段落里抽字段、对照 YAML 下结论。检索范围由代码限定，模型不能跳过章节去搜整份。

Agent 只用在两处，由模型决定下一步：

1. **跟随条款引用**。抽到「详见投标人须知前附表第 3.4 条」「按第四章评分标准」时，模型决定是否调用 `follow_reference` 跳到那一条。前附表和正文不一致时以前附表为准，这一行写两处页码。
2. **提问框**。模型在这些工具里选择和排序：`search_section`（指定章节检索）、`follow_reference`、`read_company`（读 YAML）、`calc_price_score`（按评分办法的公式算价格分）。工具都是普通函数，价格分由代码算，不由模型算。答不出就说「文件中未找到」。

## 七、升级：四层 Agent + 先定契约

```text
文档解析 Agent  ->  章节树 + 表格结构 + 页码坐标
      ↓
条款抽取 Agent  ->  条款清单，每条带出处（页码 + 坐标）
      ↓
比对 Agent      ->  差异清单：符合 / 偏离 / 缺失
      ↓
校验 Agent      ->  复核每条结论的证据是否充分
      ↓
              核对报告
```

**四个 Agent 之间只传结构化数据（JSON），不传自由文本。** 契约先定死再开工，这是唯一必须提前敲定的东西；契约没敲死就动手，后面全是返工。

这不是硬凹多 Agent，三个理由：

1. **上下文装不下**：200 页标书塞不进一个上下文，塞进去也丢约束。
2. **错误类型不同**：解析错（跨页表没合并）、抽取错（「不低于」读成「等于」）、比对错（漏偏差条款）——混在一个 Agent 里无法定位、无法修。
3. **需要独立校验**：比对 Agent 会自信地给出错误结论，必须有第二个角色只看证据够不够。

## 八、自进化：只沉淀规则，不修单题

先划一条线：

> **能沉淀成规则、下次遇到没见过的实例也有效 = 自进化。只治那一道题 = 修 bug。**

四类真能进化的问题：

| # | 问题 | 错法 | 沉淀成什么 | 怎么验证 |
|---|---|---|---|---|
| 1 | 同义术语认不出 | 要求「注册建造师」，投标写「一级建造师」，判缺失 | 同义词表 + 成立依据 | 换说法仍能匹配 |
| 2 | 否定 / 方向判反 | 「不得低于 3 年」当成「不超过 3 年」 | 句式规则 + 例外（「除…外」「除非」反向） | 造 20 条同类句式 |
| 3 | 跨页表格接不上 | 证书清单跨两页，第二页无表头，列错位 | 版式启发式（含「续」或首行数字的表格接续上页） | 10 份含跨页表文件 |
| 4 | 数值单位换算 | 「注册资本壹仟万元」vs「10,000,000 元」比较失败 | 中文大写映射 + 单位归一 | 15 个变体 |

第 1 类最值钱：**术语表从 5 条长到 80 条**，是最好看的一张图，而且它是真正的领域知识积累。

三类不要碰：边界主观的业务判断（如「类似业绩」）、一次性的版式怪癖、数据本身缺失。

机制：

```text
跑完一轮 -> 人工确认错误 -> 归因到具体环节（解析 / 抽取 / 比对）
         -> 提炼规则（触发条件 + 动作，结构化存储）
         -> 注入对应 Agent
         -> 题集全量重跑
         -> 分数涨 = 生效；分数掉 = 回滚
```

规则必须是结构化的（条件 + 动作），不能是自由文本的「心得体会」。自由文本几十条之后会互相污染，这是这套机制最容易踩的坑。

## 九、评测与指标

**已有**：8 条种子题（人工核过页码，`eval/compare.py` 三档打分）。它只锁事实不退化，不是准确率全集。

**要继续做的三块**（后两块的标准答案由脚本构造，不靠人标）：

1. **检索：先判章节 vs 整份搜**（简历主数字）
   - 从中国政府采购网和各省分网收集 20–30 份可直接下载的招标文件，货物、服务都要，代理机构模板不同
   - 每份出 3–5 道题，共 80–100 道，标好答案在哪章哪页；模型按章节出题、给候选页码，人只核对改正
   - 故意放陷阱题：同一个词两章都有，答案只在其中一章（「投标保证金多少」vs 合同里的「履约保证金」）
   - 对比「整份取前 k 段」与「先判章节再检索」；记录答案页是否命中、引用页码是否对、找不到时有没有乱答
   - 先用 5 份调规则和提示词，其余只测不回头改
2. **注入式测试**（把种子题扩到 24 题）：拿真实文件用脚本改，改了什么就是标准答案。改保证金金额 / 开标时间 / 有效期看表值是否跟着变；删掉一条 ★ 或给普通条款加 ★ 看废标表增减；正文与前附表写不同数值看是否以前附表为准并标冲突；把条款挪到别的章看「先判章节」会不会漏。每份能生成几十个变体，规模不受人工标注限制。
3. **公司情况变体**：`company.yaml` 脚本生成多份，每份故意缺一两项或改错一两项（资质等级不够、业绩年份过期、缺社保证明），缺了什么就是标准答案，统计漏报、误报。

四张表另抽 10 条/份人工核页码和原文是否对得上。

**三个指标**，三个阶段各跑一次（基线 → 第一轮进化后 → 最终）：

| 指标 | 含义 | 期望 |
|---|---|---|
| 规则库条数 | 0 → N | 证明在积累 |
| 重复错误率 | 同类错误第二次出现的比例 | 往下走 |
| **回归分数** | 题集全量通过率 | 每轮必跑，掉了回滚 |

第三个最重要——**没有它，前两个都能造假**。诚实预期：分数不会一路上涨，中间出现退化再回滚，比「从 62% 一路涨到 95%」可信得多，也是面试能展开讲的点。

## 十、两周排期

| 时间 | 目标 | 验收 |
|---|---|---|
| D1–D3 | 四个 Agent 的 I/O 契约定死，单链路拆成四段 | 每段能独立跑，输出可落盘 |
| D4–D6 | 校验 Agent（证据充分性复核） | 能拦住至少 3 个已知的幻觉案例 |
| D7–D9 | 自进化骨架：归因 → 规则库 → 注入 | 术语同义词能自动生效 |
| D10–D11 | 回归门禁 + 回滚 | 故意造一次退化，确认能回滚 |
| D12–D14 | 跑三轮，出数字，写失败案例 | 三个指标齐全 |

D1–D3 最关键。契约没敲死就动手，后面全是返工。

## 十一、简历与面试口径

**简历一行：**

> 招投标文件智能核对系统：4 个 Agent 分工（解析 / 抽取 / 比对 / 校验），自进化规则库 + 回归门禁，24 题评测集，核对准确率从 __ 提升至 __，重复错误率下降 __%；章节内检索相比整份检索，答案页命中率 X% → Y%。

数字跑完评测再填，不先写。

**面试能展开的四层，每层对应一个 JD 关键词：**

| 被问到 | 讲什么 |
|---|---|
| Agent 编排 | 为什么拆四层，契约怎么定，层间只传 JSON |
| 失败兜底 | 校验 Agent 怎么判断证据够不够，拦下了什么 |
| 评测闭环 | 24 题怎么造的，注入式评测的偏差怎么控 |
| 自进化 | 归因怎么做，规则怎么结构化，退化怎么回滚 |

追问任何一层都有细节可答——**这比四个项目各讲一层强得多**。

## 十二、边界（必须能说清）

面试官问「它什么时候会坏」，要答得出来：

- 扫描件 / 图片型 PDF：OCR 质量决定上限（第一版不支持）
- 手写体、印章覆盖文字的条款：解析不可靠
- 招标文件本身条款自相矛盾：只能标出矛盾，不能裁决
- 极度非标的私人模板：版式启发式失效

**能说清边界的项目，比号称「什么都能做」的可信。**

## 十三、不做的事

- 不开新项目，不碰爬虫和招聘平台
- 不做账号、数据库、多租户、在线下载招标文件
- 不做扫描件 OCR、Word 招标文件、工程量清单、围串标检查、资质在线验真
- 不自动写整本标书和技术方案正文（质量没法客观评，还容易写进不存在的资质）
- 不追求「任意文档自动核对」——收缩到招投标这一种版式做透

第二阶段再谈（每项先定好怎么评测再动手）：填投标文件格式（只填投标函、开标一览表、声明函、偏离表，内容全部来自 YAML 和用户报价，编造必须为 0；技术方案只列提纲标评分项）、检查投标文件草稿（注入报价超限价、有效期不足、缺授权书、大小写不一致，统计查出率）、更正公告比对、人工改判记录（同类改判两次才收成检索规则）。

## 十四、时间现实

- 距 2026-12-21 约六周
- 招投标两周收尾出数字
- 随后两周：简历按 JD 关键词重排（当前卡点是简历过不去，不是项目不够）
- 剩余时间：投递 + 面试 + 迭代

一个能讲 30 分钟不被问倒的项目 + 一份对得上 JD 的简历，比七个半成品有用。
