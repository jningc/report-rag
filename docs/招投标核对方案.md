# 招标文件核对 Agent：初步方案

## 一句话

投标人下载招标文件之后、动手写投标文件之前，用它把这份招标文件读一遍：列出会被废标的条件、评分项和分值、必须交的材料、投标文件格式里的空表，每条带页码；再拿自己的公司情况去对，标出缺什么。

个人项目。数据用政府采购网公开的招标文件，公司情况自己写一份 YAML。不生成整本标书，不判断能不能中标。

## 解决什么问题

一份政府采购招标文件通常一百到两百页，废标条件、资格要求、评分表、材料清单分散在不同章节，而且用的词很像。「保证金」「资格」「业绩」在投标人须知、评分办法、采购需求、合同里都会出现。

普通 RAG 整份一起搜，经常把评分办法里的「业绩加分」当成资格门槛，或者把合同里的保证金当成投标保证金。这个项目先判断问题该去哪一章，再只在那一章里检索。

## 先看清真实数据

找到的公开招标文件都是一个 PDF 按章节排，不是一包十几个文件。常见章节：

| 章节 | 里面有什么 |
|---|---|
| 招标公告 / 投标邀请 | 预算、最高限价、资格要求、截止和开标时间 |
| 投标人须知 | 保证金、投标有效期、密封签章、无效投标情形 |
| 资格审查 | 资格证明材料清单 |
| 评标办法 | 评分项、分值、实质性条款（常用 ★ 标出） |
| 采购需求 | 技术规格、服务要求、数量 |
| 合同文本 | 付款、履约保证金、违约责任 |
| 投标文件格式 | 投标函、开标一览表、声明函等空表 |

所以路由的单位是「章节」，不是「文件」。章节靠目录和标题切出来，切不准的用模型看标题和前几行判一次。

## 输入和输出

输入：

- 一份招标文件 PDF
- `company.yaml`：成立年限、资质证书、人员证书、近三年业绩、是否中小企业、能否交保证金

输出四张表，加一个提问框：

| 表 | 每行内容 |
|---|---|
| 废标对照 | 条件原文、出自哪章哪页、对照 company.yaml 的结论（满足 / 不满足 / 人工看） |
| 评分对照 | 评分项、分值、评分标准原文、页码、公司已有的对应材料 |
| 材料对照 | 必须提交的证明材料、页码、YAML 里有没有 |
| 空位对照 | 投标文件格式里要填的表和字段，只列出来，不代填 |

提问框只回答这份文件里的事，例如「联合体能不能投」「开标在哪」。回答带页码，找不到就说「文件中未找到」。

每一行都必须有页码。没有页码或模型没把握的，统一标「人工看」，不猜。

四张表之外，再出两张辅助表：

| 表 | 每行内容 |
|---|---|
| 时间节点 | 获取文件截止、投标截止、开标、质疑期限，各带页码 |
| 合同要点 | 付款方式、履约保证金、违约责任、验收，各带页码。只是中标后的约束，和废标表分开 |

废标表最前面单独列出带 ★（或 ▲）的实质性条款：先用正则抓标记，再由模型确认是不是「不满足即无效」。

界面上点任意一行，右侧用页图翻到对应页，并按块坐标画高亮框。没有页码或没有坐标的不画框，标「人工看」。可切换到解析文本视图核对章节切分。所有表都能导出 Excel。交互见 `项目构思/效果演示.html`。

## 架构

```text
PDF -> PyMuPDF 按页抽文本并记下块坐标 bbox -> 按目录切章节并标类型 -> 章节内切块（带章节、页码、bbox）
                                              |
                       BM25 + 向量索引（按章节类型分开）
                                              |
LangGraph 固定四步：
  1 废标：只搜 招标公告 + 投标人须知 + 资格审查
  2 评分：只搜 评标办法
  3 材料：只搜 投标人须知 + 资格审查 + 投标文件格式，再对 company.yaml
  4 空位：只搜 投标文件格式
                                              |
            每条检查有没有页码 -> 有：进表；没有：人工看
                                              |
                           四张表 + 提问框（先判章节再检索）
```

四步是每次都跑的固定任务，不是等用户提问，所以这部分是工作流，不叫 Agent。模型只做三件事：给切不准的章节分类、从段落里抽字段、对照 YAML 下结论。检索范围由代码限定，模型不能跳过章节去搜整份。

Agent 只用在两处，由模型决定下一步：

1. 跟随条款引用。抽到「详见投标人须知前附表第 3.4 条」「按第四章评分标准」这类句子时，模型决定是否调用 `follow_reference` 跳到那一条。前附表和正文不一致时以前附表为准，这一行写上两处页码。
2. 提问框。模型在这些工具里选择和排序：`search_section`（在指定章节检索）、`follow_reference`、`read_company`（读 company.yaml）、`calc_price_score`（按评分办法里的公式算价格分）。工具都是普通函数，价格分由代码算，不由模型算。答不出就回答「文件中未找到」。

## 技术选型

| 环节 | 选型 |
|---|---|
| 语言 | Python 3.11 |
| PDF 解析 | PyMuPDF，按页保留页码和块坐标 bbox；扫描件第一版不支持 |
| 章节切分 | 目录页 + 标题正则，失败时模型判一次 |
| 检索 | rank-bm25 + FAISS，按章节类型分库 |
| 向量 | 通义 text-embedding-v4，或本地 BGE |
| 编排 | LangGraph，四个固定节点 |
| 模型 | 通义千问，密钥放环境变量 |
| 结构化输出 | pydantic 定义四张表的字段，模型用 JSON 模式 |
| Agent 工具 | search_section、follow_reference、read_company、calc_price_score，均为普通 Python 函数 |
| 界面 | 表格页签 + 原件按页（页图 + bbox 高亮）+ 解析文本第二档 + 提问框。演示：`项目构思/效果演示.html` |
| 导出 | openpyxl 导出 Excel |
| 评测 | 自标题集 + 对比脚本 |

不做账号、数据库、多租户、在线下载招标文件。

## 评测

两三份文件撑不起评测，但公开招标文件并不少，真正慢的是人工标注。评测分三块，后两块的标准答案由脚本构造，不靠人标。

### 1. 检索：先判章节 vs 整份搜

这是简历上主要讲的数字：先判章节再检索，比整份一起搜少找错几次。

- 文件：从中国政府采购网和各省分网收集 20 到 30 份能直接下载的招标文件，货物、服务都要有，代理机构模板也要不同。
- 题目：每份出 3 到 5 道，共 80 到 100 道，每题标好答案在哪一章、哪一页。先让模型按章节出题、给候选页码，人只核对和改正，不从零写题。
- 故意放几道陷阱题：同一个词在两章都出现，但答案只在其中一章。例如「投标保证金多少」，合同里也有「履约保证金」。
- 对比两种做法：
  - 整份一起搜，取前 k 段
  - 先判章节，再在该章节里搜
- 记录：答案所在页是否在检索结果里；回答引用的页码是否对；找不到时有没有乱答。
- 先用 5 份文件调章节规则和提示词，其余文件只测，不回头改。

### 2. 注入式测试

拿真实招标文件，用脚本改，改了什么就是标准答案：

- 改投标保证金金额、开标时间、投标有效期，看表里的值是否跟着变。
- 删掉一条 ★ 条款，或给普通条款加上 ★，看废标表是否增减。
- 让正文和前附表写不同数值，看是否以前附表为准并标出冲突。
- 把一条条款挪到别的章，看「先判章节」会不会漏掉。

每份文件能生成几十个变体，规模不再受人工标注限制。

### 3. 公司情况变体

company.yaml 用脚本生成多份，每份故意缺一两项或改错一两项，例如资质等级不够、业绩年份过期、缺社保证明。缺了什么就是标准答案，统计材料对照和废标对照的漏报、误报。

四张表另外抽查：每份文件人工核 10 条，看页码和原文是否对得上。

## 第一版范围

1. 一份招标文件跑通：切章节、建索引、四步出表。
2. 加第二、第三份，章节切分要对三份都成立。
3. 加 ★ 条款、时间节点、合同要点和 `follow_reference`。
4. 扩到 20 到 30 份，写题集、注入脚本和 YAML 变体，跑出数字。
5. 最后做页面：表格、页图跳页并按块坐标画框、解析文本视图、提问框、导出 Excel。

先不做：扫描件 OCR、Word 招标文件、工程类带工程量清单的文件、围串标检查、资质在线验真。

## 第二阶段

基础做完、数字跑出来之后，按下面顺序加。每一项先定好怎么评测再动手。

1. 填投标文件格式。只填格式章里的投标函、开标一览表、声明函、偏离表，内容全部来自 company.yaml 和用户输入的报价。评测：字段填对的比例；有没有出现 YAML 里没有的证书、业绩、人员（编造必须为 0）；每条 ★ 条款在偏离表里有没有对应一行。技术方案只按评分项列提纲，每条提纲标明对应的评分项和分值，不写正文。
2. 检查投标文件草稿。用上一步生成的草稿，脚本注入错误：报价超最高限价、有效期短于要求、缺授权委托书、大小写金额不一致。错在哪里已知，统计查出率。公开的旧投标文件只用来对照真实格式。
3. 更正公告比对。从中国政府采购网「更正公告」栏目收集原文件和更正公告的配对，标出改了哪几条、影响哪张表。
4. 人工改判记录。每行可标「误报 / 确认」，记下条款原文、章节、结论。文件到 20 份以上，同类改判才会重复出现；这时再试「同类改判两次收成一条检索规则」，用没参与订规则的文件测，规则可删除。

不做：自动写整本标书和技术方案正文。质量没法客观评，还容易写进不存在的资质。

## 简历上怎么写

> 招标文件核对 Agent（个人项目）：针对政府采购招标文件章节多、术语重复、条款互相引用导致检索命中错章的问题，用 LangGraph 实现「先判章节再检索」的固定核对流程，输出废标、评分、材料、空位四张带页码对照表；问答部分由 Agent 调用章节检索、条款引用跳转、价格分计算等工具。在 N 份公开招标文件、M 道题上，答案页命中率由整份检索的 X% 提升到 Y%，陷阱题错引次数由 A 降到 B；注入式测试中前附表冲突识别率为 Z%。

N、M、X、Y、A、B、Z 跑完评测再填，不先写。
